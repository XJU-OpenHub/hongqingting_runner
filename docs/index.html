一、项目说明

本项目以 hongqingting.py 为案例，演示一类典型的"客户端伪造数据上报"脚本是如何工作的，并以此为切入点讲解：

  • HTTP 请求构造（form-urlencoded、Python-dict 风格 body、URL 编码）
  • 密码盐 (salt) + MD5 散列鉴权
  • gzip 压缩传输
  • 浏览器同源策略 / Mixed Content / CORS 的拦截原理
  • 服务端如何对客户端伪造的数据做识别与防御
使用须知。 脚本会向远端 HTTP 服务器发送真实请求。请只把目标地址指向 你自己授权、自己控制的服务器（例如本文第四节的 mock）。 在没有授权的情况下用脚本对接生产系统提交数据，属于伪造提交，违反学术诚信和大多数地方法律法规，本课程材料明确不为此提供帮助。

二、为什么必须本地运行（这一页不能直接跑）

很多同学第一反应是："为什么不把脚本搬到 GitHub Pages 上点一下就跑？"答案藏在两道浏览器安全墙里——而它们正是今天要讲的第一个知识点。

2.1 Mixed Content（混合内容）

本页托管在 https://<org>.github.io/...。GitHub Pages 强制 HTTPS。脚本里的目标地址却是 http://...。

现代浏览器规则：

从 HTTPS 页面发出的、指向 HTTP 资源的请求，一律拦截。

请求根本不会出网卡。Console 里你能看到的报错长这样：

Mixed Content: The page at 'https://...' was loaded over HTTPS,
but requested an insecure resource 'http://...'.
This request has been blocked; the content must be served over HTTPS.

2.2 CORS（跨源资源共享）

就算混合内容这关过了（比如把页面也用 HTTP 起本地 server），还有第二道墙：浏览器的同源策略要求跨源请求需要服务器返回 Access-Control-Allow-Origin 头。脚本指向的服务器并不会下发这个头，所以浏览器即便收到了响应也会丢掉，并向 JS 抛出：

Access to fetch at 'http://...' from origin 'http://localhost:8000'
has been blocked by CORS policy: No 'Access-Control-Allow-Origin'
header is present on the requested resource.

2.3 为什么 Python requests 没事

Mixed Content 和 CORS 都是 浏览器层面的安全机制，目的是防止恶意网站拿你的浏览器去打别人。requests 是普通 HTTP 客户端，不是浏览器，不受这两道墙约束——所以你看到 Python 脚本能跑、网页跑不通。这是设计如此，不是 bug。

能力Python requests浏览器 fetch
HTTPS → HTTP 请求允许拦截 (Mixed Content)
跨源请求允许需服务端 CORS 头
修改 User-Agent允许禁止
修改 Origin / Referer允许禁止
读取任意 Cookie允许受 SameSite / HttpOnly 限制
课程小结。 浏览器里写代码 ≠ 服务器/CLI 里写代码。前端能做什么受同源策略、Mixed Content、CSP 等多重约束。 要在浏览器里实现 requests 能做的事，就必须在自己控制的服务器上做一层代理——而这层代理本身又会成为下一节"反作弊"要重点防的东西。

四、自建 Mock 服务器（教学推荐用法）

我们 强烈建议 在课堂演示中只把脚本指向一台你自己控制的本地 mock，原因有二：

  1. 讲到反作弊时，需要看到 请求 → 解码 → 服务端判定 整条链路，这只有自己能控的 mock 才看得到。
  2. 避免触碰生产系统，确保教学合规。

下面这份 mock_server.py 用 Flask 实现了三个端点，并对上传 body 做最简单的反作弊检测，作为下文第七节的演示靶子：

"""mock_server.py — 教学用红蜻蜓接口 mock。
依赖: pip install flask flask-cors
启动: python mock_server.py        # 默认监听 5000
"""
import gzip, json, time, ast, re
from flask import Flask, request, jsonify
from flask_cors import CORS

app = Flask(__name__)
CORS(app)  # 教学环境放开所有来源；生产应只放白名单

def maybe_gunzip(raw: bytes) -> str:
    """body 可能是 gzip，按 magic bytes 自检."""
    if len(raw) >= 2 and raw[0] == 0x1f and raw[1] == 0x8b:
        return gzip.decompress(raw).decode('utf-8', errors='replace')
    return raw.decode('utf-8', errors='replace')

def parse_pyobj(body: str):
    """脚本 body 是 Python-dict 字面量风格（单引号），用 ast.literal_eval."""
    try:
        return ast.literal_eval(body)
    except Exception:
        return None

# ---- 反作弊检测函数（详见第七节） ----
def detect_fraud(payload: dict):
    issues = []
    try:
        usetime = float(payload['usetime'])
        distance = float(payload['distance'])
        # 配速合理性：人类极限约 2.8 min/km；步行约 12 min/km
        speed = (usetime / 60) / (distance / 1000)
        if speed < 2.8 or speed > 12:
            issues.append(f'配速异常 {speed:.2f} 分钟/km')
        # 时间区间
        begin, end = int(payload['begintime']), int(payload['endtime'])
        if end - begin != usetime + (end - begin - usetime):
            pass  # （留作学生补全：检验 begin/end/usetime 一致性）
        # 轨迹时间戳单调性
        loc = payload.get('location', '')
        ts = [int(p.split(';')[1]) for p in loc.split('@') if ';' in p]
        if any(b < a for a, b in zip(ts, ts[1:])):
            issues.append('轨迹时间戳非单调递增')
        # 轨迹点数 vs 时长（采样率合理性）
        if ts and (ts[-1] - ts[0]) / max(len(ts) - 1, 1) > 30:
            issues.append('采样间隔过大（> 30 秒/点），可疑')
    except Exception as e:
        issues.append(f'解析失败: {e}')
    return issues

@app.post('/cloud/DflyServer')
def auth():
    body = request.get_data(as_text=True)
    print('[AUTH]', body[:200])
    return jsonify({'status': 'ok', 'echo': body})

@app.post('/DragonFlyServ/Api/webserver/getRunDataSummary')
def summary():
    body = maybe_gunzip(request.get_data())
    print('[QUERY]', body[:200])
    return jsonify({'m': 12345, 'lasttime': int(time.time()), 'echo': body})

@app.post('/DragonFlyServ/Api/webserver/uploadRunData')
@app.post('/DragonFlyServ//uploadRunData')  # 1.16km 变体路径
def upload():
    body = maybe_gunzip(request.get_data())
    print('[UPLOAD]', body[:300])
    payload = parse_pyobj(body)
    issues = detect_fraud(payload) if payload else ['body 解析失败']
    if issues:
        print('  ⚠️ 反作弊命中:', issues)
        return jsonify({'status': 'reject', 'issues': issues}), 200
    return jsonify({'status': 'ok'})

if __name__ == '__main__':
    app.run(host='0.0.0.0', port=5000, debug=True)

启动它：

pip install flask flask-cors
python mock_server.py

然后改 hongqingting.py 里的目标 URL 指向 http://127.0.0.1:5000/...，再 python hongqingting.py。整个流程不碰任何生产服务器。

五、请求结构剖析

5.1 登录请求 — 密码盐 + MD5 + URL 编码列表

# hongqingting.py 摘录
password = 'Stu' + no                      # ① 密码盐 + 学号
md5_password = hashlib.md5(password.encode()).hexdigest()  # ② MD5 散列
data = ("name=%5B%27bangding%27%2C%2710755%27%2C%27student%27%2C%27"
        + no + "%27%2C%27" + md5_password + "%27%5D")      # ③ 拼接

解码后这串 name= 实际等价于：

name=['bangding','10755','student','<学号>','<md5(Stu+学号)>']

其中 %5B 是 [，%27 是 '，%2C 是 ,，%5D 是 ]。整个数组被当成一个字符串放在 form-urlencoded 的 name 参数里——这是个不太常见的 API 设计，服务端实际会再做一次反 URL 编码 + 反序列化。

知识点

  • 密码盐 (salt)：固定前缀 Stu 拼接学号后再 MD5。这种"固定盐 + 用户标识"的做法本质上 不是真正的盐——真正的盐应当随机、按账户存储。这种做法只是"轻微混淆"，被反编译看到一次就全网破解。
  • MD5：已被证明不抗碰撞，2026 年的密码学课不会推荐它做任何安全用途；但在协议逆向时仍很常见，因为很多老 API 在用。
  • URL 编码：把任意字节安全地塞进 application/x-www-form-urlencoded。要让学生熟练在脑里把 %XX 翻译回字符。

5.2 查询里程 — gzip + Python-dict 风格 body

data = ("{'studentno':" + no
        + ",'uid':'<固定 UID>'"
        + ",'schoolno':'10755'}")
gzip_data = gzip.compress(bytes(data, 'utf-8'))
resp = requests.post(url, headers=headers, data=gzip_data)

注意几点：

  • body 是 Python 字典字面量字符串（单引号），不是标准 JSON。服务端需要 ast.literal_eval 或自定义解析（用 json.loads 会失败）。
  • 整个 body 用 gzip 压了一遍，但请求头 没有显式声明 Content-Encoding: gzip——靠服务端按 magic bytes 1f 8b 自检。这种隐式压缩在野生 API 里相当多。
  • 'studentno' 的值 不带引号（看起来像数字），其它字段都带引号。这种"不一致的引号风格"也是 API 自家拼字符串、未走标准序列化的强信号。

5.3 上传跑步数据 — 真正的"伪造载荷"长什么样

data = ("{'begintime':'" + str(begintime)
        + "','endtime':'" + str(endtime)
        + "','uid':'" + uid + "'"
        + ",'schoolno':'10755'"
        + ",'distance':'" + f"{distance:.1f}" + "'"
        + ",'speed':'" + str(speed) + "'"
        + ",'studentno':'" + no + "'"
        + ",'atttype':'3','eventno':'803'"
        + ",'location':'" + loc_r + "'"          # ← 改写后的轨迹串
        + ",'pointstatus':'1'"
        + ",'usetime':'" + str(usetime) + "'"
        + ",'path':'null'}")
gzip_data = gzip.compress(bytes(data, 'utf-8'))

关键字段语义：

字段含义反作弊检测点
begintime / endtime开始/结束 Unix 秒是否跨午夜？是否在合法运动时段？
distance米，1 位小数与 usetime 算出的配速是否物理合理？
usetime用时秒数是否 ≈ endtime - begintime？
speed分钟/km，浮点是否 = (usetime/60) / (distance/1000)？字段间一致性
uid设备指纹同一设备短期是否重复提交？同一 UID 跨学号？
location轨迹点串，见下节时间戳单调？两点间距与时差是否合理？是否与历史轨迹高度相似？
atttype / eventno / pointstatus / path固定常量固定值意味着这些字段服务端可能根本没看，或保留给未来用

六、轨迹文件格式

仓库里 location_*km 是预录好的真实轨迹（每一行就是一段路线，按 @ 分隔每个采样点）。单个采样点格式：

<lat,lng>;<timestamp>;null;null;<displacement>;null@

例如：

43.85163360905115,87.7355488539563;1683710085;null;null;0.0;null@

脚本上传前做的事情很简单（关键算法）：

points = re.findall(r'.*?@', text)
delta_time = usetime / len(points)            # 等分时长
runtime = begintime
for item in points:
    loc = re.match(r'(.*?);', item).group(1)  # 取出 lat,lng
    item = re.sub(r'.*?;.*?;null;null;',
                  f'{loc};{int(runtime)};null;null;', item)
    out += item
    runtime += delta_time

也就是 坐标不动、时间戳重写。这是这一类伪造工具最廉价、最常见、也最容易被识破的核心套路。

为什么这种重写容易被识破

  • 采样间隔太均匀：真实跑步 GPS 采样间隔会受信号波动影响（隧道、楼宇间），而这里直接 delta_time = usetime / N 平均分配，每两个点之间的间隔几乎完全相等。
  • 坐标完全复用：同一个学生反复上传同一段轨迹，统计上就是几乎 1:1 的轨迹相似度。
  • 位移与时差脱钩：真实运动中两点位移和时差有强相关；这里两点位移来自老轨迹，时差来自新分配，二者在物理意义上不再匹配（你可以让学生算一下"瞬时配速分布"）。

七、服务端反作弊视角

切换视角：你是后端工程师，怎么识别上一节那种伪造？这里给一份从易到难的检测清单，可作为大作业题目。

层级检测点实现难度能识别什么
L1 自洽性endtime - begintime ≈ usetime；speed = (usetime/60)/(distance/1000)★字段间互相算不平的低级伪造
L1 物理可行配速在 [2.8, 12] 分/km；距离 / 时长在合理范围★填错数量级的批量发包
L2 时间begintime / endtime 落在校规允许的运动时段；不跨夜★定时脚本在凌晨刷里程
L2 轨迹自洽轨迹时间戳单调；两点间距 / 时差 → 瞬时速度也要在物理合理范围★★"坐标不动、时间戳重写" 这一类
L3 设备UID 在短期内是否给多个 studentno 用过；同一 studentno 是否短期换 UID★★共享脚本 / 设备指纹复用
L3 轨迹去重把每条轨迹做 hash 或几何相似度比对，和历史比；命中阈值即拒★★★预录轨迹反复上传
L4 行为画像同一账号每周配速/总里程的分布：方差骤降 / 中位数恒定 → 可疑★★★长期 + 隐蔽的批量伪造
L4 客户端绑定App 内做轨迹签名（HMAC + 设备私钥），服务端校验签名而非裸数据★★★★从协议层禁掉脱机伪造（但攻防永无止境）

第四节的 mock_server.py 实现了 L1 + L2 的一个简化版（detect_fraud 函数），可以作为起点让学生扩展到 L3 / L4。

讨论。 为什么真实生产里很少看到 L4 的客户端签名？提示：会显著增加 App 开发复杂度、被动手反编译破解（参考 frida、JustTrustMe 等工具）、还要面对刷机用户。 安全从来不是"绝对防得住"，而是"把攻击成本抬到收益不划算"。

八、思考与练习题

基础

  1. 用 mock_server.py 跑一遍。在 Console 看到的 body 是什么样的？回答："application/x-www-form-urlencoded 的 body 后面接一段 gzip 字节"——这种混合头部和编码的请求，浏览器 fetch 写出来会有什么坑？（提示：Content-Type 头怎么写？Content-Encoding 要不要写？）
  2. 把 'Stu' + no 改成 'NotStu' + no，登录会失败吗？为什么？
  3. 把 schoolno 改成一个不存在的代码，服务端 mock 怎么响应？真实服务端会怎样？

进阶

  1. 扩写 detect_fraud：实现"轨迹去重"——记录每个学号近 30 天提交过的所有 location 串，新提交时计算与历史的几何相似度（Hausdorff 距离 / DTW / 简单 hash），高于阈值即拒。
  2. 在客户端给 location 增加 HMAC 签名，签名 key 由服务端在登录时返回（短期有效）。修改 mock 让它校验签名。讨论攻击者如何绕过（提示：内存抓 key、动态 hook）。
  3. 用 mitmproxy 抓真实运动 App 的请求，对比本案例中的 body 结构，列出至少三处差异。

开放

  1. 同样的伪造手法应用到打卡考勤、健康码、消费数据上有什么社会影响？设计一份"以防御为主"的安全课大作业题目，从协议层、应用层、行为分析层各给一道任务。
